## 1. 目标与范围

博客下一阶段按三个阶段推进：

1. 先完成博客统一内容模型和 API 契约迁移。
2. 再完善作者创作闭环（A）。
3. 最后完善读者发现与留存（B）。

本计划首期覆盖 `Atoman-Frontend` 与 `Atoman-Backend`。iOS 暂不同时实现，但新增 API 和数据模型需要保留后续接入空间。

## 2. 当前基线

以下能力视为现有基线，不作为本计划的重复开发范围：

- 多个独立作者的文章、作者主页和频道内容。
- 作者频道、合集、草稿、发布和基础编辑流程。
- 频道由作者用户拥有，创建频道时自动创建默认博客合集；频道的增删改由频道拥有者负责。
- 合集属于频道，不是独立的用户资源；创建、修改和删除由频道拥有者负责，默认合集受保护。
- 当前 legacy 文章支持单个 `collection_id` 和 `post_collections` 多合集关系；迁移后以统一合集关联为唯一来源。
- Backend 正在并行维护 legacy `Post/Collection` 与 unified `ContentEntry/ContentCollection`；博客现有读写契约仍以 legacy 模型为主，统一模型由迁移和 Studio 能力逐步承接。
- 文章阅读、订阅时间线、收藏、稍后阅读、评论和基础互动。
- 订阅对象包括用户、频道和合集；三类内容进入统一时间线，按发布时间排序，同一文章去重并标注来源。
- 基础推荐、RSS、SEO、可见性控制和基础作者数据统计。
- 现有的文章状态、关注者可见性、私密内容和管理员权限边界。

已确认的产品边界：

- 作者可以直接发布，不设置所有文章统一审核流程。
- 只有文章作者本人和管理员可以编辑文章，不开放跨用户协作编辑。
- 作者可以拥有多个频道，并自行管理频道和合集。
- 已发布文章删除采用下架/归档，默认不立即物理删除。
- 频道首期只支持作者/拥有者维护，读者通过用户、频道或合集订阅获取内容。
- 统一订阅时间线混合展示三类来源，按发布时间排序；同一文章命中多个订阅时只展示一次，并标注订阅来源。
- 暂不建设站内通知或邮件通知，订阅者通过订阅时间线查看新文章。
- 不把本计划扩展为团队出版、作者邀请、审核队列或复杂运营后台。

## 3. 前置阶段：博客统一模型迁移

目标：将博客从 legacy `Post/Collection` 业务契约迁移到统一的 `ContentEntry/ContentCollection` 模型，迁移完成后不保留 legacy 博客 API、DTO 或业务读写兼容层。

统一模型边界：

- `ContentEntry` 作为文章的 canonical 内容实体，统一承载频道、类型、标题、摘要、封面、状态、可见性、发布时间和定时发布时间等公共字段。
- 统一模型必须补齐文章作者关系；当前 `ContentEntry` 没有 `AuthorID`，不能只从 `Post.ChannelID` 回填，否则会改变作者编辑权限和作者订阅语义。
- 当前 `ContentPostExtension` 只有 `ContentID -> PostID` 关联，不足以承载最终博客模型；迁移阶段必须增加或替换为博客专用扩展，承接正文、语言、置顶、浏览量及其他博客特有字段。
- `ContentCollection` 作为频道范围内的统一合集，保留频道归属、创建者、默认合集和合集元数据。
- `ContentCollectionMembership` 作为文章与合集的唯一关联来源，支持文章归入多个合集。
- `LegacyCollectionMapping` 只用于一次性迁移校验；迁移完成并验证通过后删除，不进入运行时业务路径。

迁移内容：

- 盘点所有依赖 `Post`、`Collection`、`PostCollection` 和旧文章 ID 的 Backend 模块，包括博客读写、草稿、发布、SEO、RSS、Feed、推荐、评论、点赞、收藏、稍后阅读、评分、举报和资源引用。
- 先补齐统一博客扩展和作者关系，再定义统一实体 ID、状态、可见性、作者、频道、合集、错误响应和分页 DTO；统一模型成为唯一读写来源，不做 dual-read 或 dual-write。
- 将历史文章、作者、合集、文章合集关系、版本、草稿、互动目标和类型扩展数据回填到统一表，并校验数量、唯一性、频道归属、默认合集和关联完整性。
- 迁移 Backend 服务、仓储、HTTP 路由和授权判断；旧 legacy API 不作为兼容入口保留，新的 API 契约同步更新接口文档。
- 迁移 Frontend 的 API 类型、状态、编辑器、详情页、频道页、合集页、Feed、互动和测试；Frontend 与 Backend 在同一契约切换后运行。
- 迁移所有订阅源解析，使作者、频道和合集订阅直接解析统一实体；统一时间线仍按发布时间排序、去重并标注订阅来源。
- 完成切换后移除 legacy 业务代码、旧路由契约和迁移映射；旧物理表仅在确认没有残余引用后再清理，不以删除表作为迁移成功的前提。

迁移原则：

- 历史文章、草稿、发布状态、可见性、作者和频道归属不得丢失；无法自动映射的数据进入显式失败清单，不静默丢弃。
- 迁移期间不改变既有公开可见性和权限语义；新统一授权函数成为后续所有文章查询的唯一判断入口。
- 版本、草稿、评论、互动、评分、收藏、稍后阅读、订阅和推荐中的文章引用必须统一指向 canonical `ContentEntry`，不得继续以 `PostID` 作为业务身份。
- 不为旧客户端保留旧字段语义、旧响应格式或旧行为；客户端和服务端一起完成契约切换。
- 迁移失败使用数据库备份、检查点和前向修复恢复，不通过长期兼容层兜底。

验收标准：

- 历史文章、合集、合集关系、评论、互动、评分、订阅、Feed、SEO、RSS 和资源引用均能通过统一实体正确访问。
- Backend 运行时不再以 legacy 博客模型作为业务实体读取或写入；代码搜索和测试确认没有残余业务路径。
- Frontend 不再依赖 legacy DTO、字段别名或旧文章/合集 ID 语义。
- 作者、管理员、公开用户、关注者和私密文章的权限结果与迁移前一致。
- 统一 API 文档、数据库迁移记录、失败清单和回滚/恢复步骤完整，且 Frontend、Backend 构建和受影响测试通过。

## 4. A 阶段：作者创作闭环

### A1. 发布级版本与恢复

目标：让作者可以安全修改和恢复已发布内容。

产品行为：

- 每次成功发布或重新发布生成一个不可变版本。
- 服务端自动保存只更新当前草稿，不生成版本。
- 每篇文章只保留当前服务端草稿，客户端负责短期本地恢复。
- 作者可以查看自己的发布版本列表。
- 恢复历史版本后回到草稿状态，必须再次发布才影响公开内容。
- 只有作者本人和管理员可以查看、恢复和操作文章版本。
- 归档文章保留版本与关联数据，公开页面不再展示。

建议实现边界：

- 版本至少保存正文、标题、摘要、可见性、频道、合集、标签和封面等发布元数据。
- 版本创建和文章公开状态变更必须在同一业务事务中完成。
- 历史版本保存当时的正文和资源引用，媒体资源本身保持不可变，不为每个版本重复复制图片。
- 首期不做逐字 diff、协作者版本合并和版本评论。
- 版本保留时长、容量上限和管理员永久清理规则在技术设计阶段确定。

### A2. 定时发布

目标：作者可以提前准备并按预定时间公开文章。

产品行为：

- 发布时间按作者当前浏览器时区解释，后端转换为 UTC 保存，并同时保存创建时的时区标识。
- 定时计划界面显示本地时间和时区名称；作者更换设备或时区后仍按原时区显示。
- 定时文章仍可编辑和改期。
- 作者取消定时发布后，文章回到草稿状态，不对外公开。
- 到达发布时间后自动执行发布。
- 任务失败时自动重试，发布操作必须幂等，不能重复生成公开版本。
- 重试采用有限窗口，覆盖约 24 小时，例如 `1 分钟、5 分钟、30 分钟、2 小时、6 小时、12 小时`；超过上限标记为失败。

建议实现边界：

- 初期优先使用数据库任务记录、领取租约和后端轮询，不立即引入独立消息队列。
- 任务需要明确的待执行、执行中、已完成和失败重试状态。
- 文章修改、改期、取消和发布任务之间需要有并发保护，避免旧任务覆盖新计划。
- 最大重试次数、退避间隔、失败提示和管理员重试入口在技术设计阶段确定。

### A3. Markdown 导入与导出

目标：支持迁移、备份和降低平台锁定。

导入行为：

- 支持 Markdown 文件导入。
- 导入先创建草稿并提供预览，不直接公开。
- 跨作者或跨实例导入时，按 slug/名称尝试匹配频道和合集；匹配不到时保留为待确认字段。
- 导入文章的作者归属、可见性和发布时间不直接沿用，必须由当前作者确认。
- 站内图片下载后复制为当前文章的独立资源，并替换为平台资源引用。
- 站外图片不下载、不重新托管，保留原始 URL。
- 无法识别的嵌入保留原始 Markdown，并提示作者确认。
- 导入失败时保留可诊断的错误信息，不产生半成品公开文章。

导出行为：

- 导出为 ZIP 备份包。
- 只导出当前文章版本，不打包历史版本。
- 包含 Markdown、front matter、图片和附件。
- front matter 包含标题、摘要、slug、可见性、频道、合集、作者标签、发布时间和更新时间。
- Markdown 中的资源引用使用相对路径，支持离线查看和再次迁移。
- 导出只包含用户有权访问的文章和资源。

安全与边界：

- 后端处理站内媒体复制时限制协议、域名、大小、超时和重定向，避免 SSRF。
- 对上传文件执行类型、大小和恶意内容校验。
- 首期不承诺兼容所有第三方编辑器的自定义嵌入语法。

## 5. B 阶段：读者发现与留存

### B1. 结构化博客搜索

目标：让读者按明确字段找到文章，不立即引入全文或语义搜索。

搜索字段：

- 标题。
- 摘要。
- 作者。
- 频道。
- 合集。
- 标签。

产品行为：

- 严格复用文章当前可见性规则。
- 不向无权用户泄露关注者文章或私密文章。
- 默认按相关性和更新时间排序。
- 采用一个关键词搜索框和可选筛选器；关键词、作者、频道、合集和标签筛选全部按 AND 组合。
- 标题和摘要使用包含匹配；作者、频道、合集使用名称包含匹配；标签使用规范化后的精确匹配。
- 相关性由匹配字段加权和更新时间衰减共同决定，标题权重最高；同等相关性下优先较新的文章。
- 首期不做正文全文索引、语义搜索和复杂搜索语法。

技术边界：

- 优先复用 PostgreSQL 查询和必要索引。
- 搜索条件、排序和分页需要形成稳定 API 契约。
- 搜索结果与推荐结果使用相同的可见性过滤函数，避免规则分叉。
- 结构化字段使用规范化后的标签搜索键，展示时保留原始标签显示名。

### B2. 作者标签与公共用户标签

目标：利用作者分类和读者贡献增强文章发现。

展示区域：

- 作者标签：由作者维护，代表作者对文章的正式分类。
- 用户标签：由读者贡献，作为公共标签展示，并参与搜索。

产品行为：

- 所有登录用户都可以添加公共用户标签。
- 系统限制标签长度、数量、重复值和添加频率。
- 每篇文章最多 10 个作者标签和 10 个公共用户标签。
- 标签显示名保留用户输入，搜索键去除首尾空格、合并连续空格并统一大小写比较。
- 作者标签按作者设置顺序展示；公共用户标签按使用次数降序，再按最近使用时间排序。
- 公共用户标签只展示标签名称和使用次数，不展示贡献者身份。
- 用户只能撤回自己添加的公共标签。
- 作者和管理员可以移除任意公共用户标签。
- 通过举报和合并机制处理滥用、重复和低质量标签。
- 标签首期只用于博客文章。
- 标签只作为文章展示和搜索筛选能力，不建设独立标签聚合页、标签导航或标签关注。

未纳入首期：

- 个人私有标签。
- 跨音乐、视频、播客等模块的统一标签系统。
- 标签投票、社区阈值隐藏和复杂标签治理后台。

### B3. 个性化推荐增强

目标：在现有推荐基础上提升内容匹配度，同时保留读者控制权。

行为信号：

- 显式行为：订阅、点赞、收藏、稍后阅读和关注频道。
- 阅读行为：打开文章、阅读进度和完成阅读。

产品行为：

- 基于上述信号调整推荐排序。
- 提供全局“按时间顺序浏览”开关。
- 开关保存到用户账号并跨设备同步。
- 关闭个性化后，推荐页回退到非个性化的时间顺序。
- 新用户没有行为数据时，使用新鲜度与内容热度的混合策略。
- 个性化排序不得扩大文章可见范围。
- 个性化事件保留最近 90 天，账号删除时一并清理。
- 提供“清除个性化数据”操作，清除后推荐画像重置并重新进入冷启动。
- 清除后个性化开关保持开启。
- 关闭个性化后停止用于排序，但不影响基础阅读记录。

首期不做：

- “不感兴趣”反馈。
- 主题屏蔽和复杂偏好中心。
- 推荐理由展示。
- 邮件或站内通知。

## 6. 内容治理与安全

治理模式：

- 采用发布后治理，作者可以直接发布，不设置统一发布前审核。
- 举报对象包括文章、评论和公共用户标签。
- 仅登录用户可以举报，举报记录与账号绑定并受到频率限制。
- 举报采用固定理由 + 可选补充说明；“其他违规”必须填写补充说明。

举报理由：

- 低质量内容：重复刷屏、无意义灌水、批量广告、标题党、误导性摘要和夸大宣传。
- 鼓吹暴力、仇恨或歧视：只针对实际鼓励、煽动或美化相关行为的内容；新闻、学术、历史和正常语境下的虚构作品不自动违规。
- 侵犯隐私：未经同意公开可识别的个人信息或私人内容，包括联系方式、精确位置、身份信息、私人通信和账号凭证；正常引用公开资料不自动违规。
- 侵权或盗版：任何登录用户都可以举报疑似侵权或盗版，并提供来源链接或补充说明；正常引用、评论和合理使用不自动违规。
- 诈骗或诱导：明确骗取钱财、账号凭证或个人信息，钓鱼链接、虚假交易、恶意跳转和伪装身份；普通广告和观点表达不自动归入此类。
- 其他违规：必须填写补充说明，由管理员在复核时重新归类或驳回。

自动隐藏与复核：

- 同一对象在 7 天内收到 3 个不同登录用户的有效举报后，自动从公开页面隐藏。
- 内容保留为“待复核”状态，原文和举报上下文只对管理员可见；作者可以看到状态。
- 同一用户对同一对象只保留一个有效举报；举报被驳回后，除非内容发生实质变化，否则不能重复计入阈值。
- 作者只能提交一次申诉，不能在待复核期间修改原内容。
- 管理员复核结果只有两类：驳回举报并恢复公开，或维持隐藏并归档。
- 复核结果反馈给举报者和作者，但不暴露举报者身份或其他举报细节。
- 首期不加入警告、限流、禁止发布、永久删除和作者账号处罚。

## 7. 跨平台分发与 RSS

目标：在不开放回写和用户私有数据的前提下，让公开博客内容能够被标准 RSS 客户端订阅。

范围：

- 只提供 RSS，不开放公共 API。
- 外部平台不能通过 RSS 回写或修改文章。
- 提供作者、频道和合集三类公开 feed。
- 暂不提供标签 RSS，避免公共用户标签产生大量不稳定的 feed。

内容行为：

- feed 只输出当前有权公开的文章。
- 每个条目输出完整正文，而不是只有摘要和站内链接。
- 正文中的图片和附件使用订阅客户端可访问的绝对 URL。
- 文章修改或重新发布时保持稳定 GUID，只更新条目内容和更新时间，不生成重复条目。
- 文章归档后从后续 feed 中移除，Atoman 不继续主动传播已归档文章。
- 平台默认开启 RSS，作者可以按作者或频道关闭；首期不做单篇文章 RSS 开关。

安全与兼容：

- RSS 输出继续复用文章公开可见性判断，不输出关注者或私密文章。
- XML、CDATA、HTML 清洗、Unicode 截断和媒体 URL 必须保持合法且可解析。
- feed 需要有限缓存和请求限流，避免高频抓取影响博客 API。

## 9. 跨端与工程要求

- 本轮实现范围为 Frontend + Backend，iOS 后续接入。

- 定时发布、导入媒体和推荐任务需要可观测的日志与失败状态。
- 所有涉及文章内容的查询都必须复用统一可见性判断。
- 前端每个阶段至少运行 `bun run type-check` 和受影响的 Vitest；跨页面行为增加 Playwright 验证。
- 后端每个阶段至少运行 `gofmt`、相关测试和 `go build ./...`。
- 未经单独确认，不修改 iOS 客户端，不引入邮件通知，不建设完整审核流。

## 12. 可执行实施计划

### 12.1 执行约束

- `ContentEntry.ID` 是文章唯一业务身份；后续实现不得新增基于 legacy `Post.ID` 或旧合集 ID 的 API 语义。
- 迭代 0 是后续工作的阻断依赖。新能力只能读写统一模型，不为 legacy 表增加双写或兼容接口。
- 每个迭代按“冻结契约和迁移方案 -> Backend -> Frontend -> 自动化与视觉验收”执行；API 变更、Swagger 和客户端调用在同一合并批次完成。
- 数据迁移必须可重复运行，输出源/目标计数、一致性校验和失败清单；用备份、检查点与前向修复恢复，不建立长期回退分支。
- 每阶段结束前运行 Backend 相关测试及 `go build ./...`，Frontend 相关 Vitest、`bun run type-check` 和关键桌面/移动流程的 Playwright 验证。

### 12.2 迭代 0：统一模型迁移与契约切换

**目标：** 将当前部分 canonical 实现完成为唯一运行时契约，删除将统一实体投影为 legacy `Post/Collection` 的过渡层。

1. **冻结范围与数据校验**
   - 盘点 `Post`、`Collection`、`PostCollection`、旧文章 ID 和旧 DTO 在 Backend、Frontend、Swagger、Feed、SEO、RSS、评论、互动、收藏、稍后阅读、推荐及资源引用中的读写点。
   - 为文章、作者、频道、合集、合集成员、版本、草稿、互动目标和资源引用定义回填校验 SQL：计数、唯一性、归属、默认合集和引用完整性；无法迁移的数据进入显式失败清单。
   - 确定 `ContentEntry`、博客扩展、草稿、版本、`ContentCollection` 与 membership 的字段归属、状态机和删除/归档语义。

2. **完成 Backend canonical 读写**
   - 将博客 service、repo、handler 和可见性判断改为 canonical DTO；删除仅维持旧 `Post/Collection` 响应形状的转换代码。
   - 将评论、点赞、评分、举报、收藏、稍后阅读、订阅时间线、推荐、SEO、RSS 和资源引用改以 `ContentEntry.ID` 为目标，且复用同一可见性授权函数。
   - 将频道、合集、默认合集和成员排序统一到 `ContentCollection`；切换完成后运行时不得查询 legacy collection mapping。
   - 替换 Swagger 中的旧请求/响应和错误定义，移除 legacy 路由，不提供兼容入口。

3. **回填、切换与清理**
   - 先在备份环境运行回填和全部校验；生产顺序固定为备份、检查点、迁移、校验、开放流量。
   - 观察期只保留只读迁移审计；确认无运行时引用后删除 mapping、legacy 业务代码和未被其他模块使用的旧物理结构。

4. **迁移 Frontend 与验收**
   - 替换文章、频道、合集、编辑器草稿、列表、详情、订阅时间线和 Studio 调用中的 legacy 类型及字段语义；路由仍只表达空间内位置。
   - 补充历史数据访问、作者/管理员/匿名用户权限、默认合集、多个合集、归档和资源引用的 API/E2E 测试。
   - 发布门槛：代码搜索不存在 legacy 博客业务读写；数据校验通过或失败清单已处理；Swagger、Backend 构建、Frontend 类型检查和关键 E2E 通过。

### 12.3 迭代 1：发布版本与归档

**开始前冻结：** 版本快照字段、分页上限、保留期限和管理员永久清理规则。

1. 增加不可变发布版本模型、迁移和索引；草稿仅保存当前编辑态，版本创建与公开状态变更处于同一事务。
2. 在发布、重新发布、恢复、归档和取消归档服务中实现状态机；恢复版本只创建草稿，必须再次发布。
3. 提供作者/管理员版本列表、读取、恢复和归档 API；其他用户不得枚举版本或访问归档内容。
4. 在编辑器和 Studio 增加版本列表、恢复确认、归档状态与再次发布流程。
5. 验收：并发发布不产生重复版本；权限边界正确；归档内容从公开查询、推荐和 RSS 中移除而历史数据保留。

### 12.4 迭代 2：定时发布

**开始前冻结：** 轮询间隔、租约时长、最大重试次数、错误分类和任务指标。

1. 增加定时任务表，保存文章 ID、UTC 时间、原始时区、状态、租约、尝试次数、下次运行时间和错误摘要。
2. 实现创建、改期、取消、领取、幂等发布和有限退避重试；文章编辑、取消和 worker 领取使用事务锁或版本条件。
3. 提供作者任务状态 API、结构化日志和指标，不引入消息队列。
4. 编辑器按创建时区录入和展示计划，支持改期、取消，并以服务端状态为准。
5. 验收覆盖服务重启、重复领取、临界改期、发布失败、重复请求和权限拒绝，且公开版本只生成一次。

### 12.5 迭代 3：Markdown 导入与导出

**开始前冻结：** 文件/媒体上限、MIME 白名单、站内媒体 URL 规则、下载超时和重定向上限。

1. 定义导入任务、诊断记录和临时草稿生命周期；解析 Markdown/front matter 后只创建预览草稿。
2. 对站内媒体复制执行协议、域名、大小、超时、重定向、类型和内容校验；站外 URL 保留原样，无法识别嵌入返回诊断。
3. 导出当前版本 ZIP，包含 Markdown、front matter、已授权资源和相对路径；按文章和资源权限过滤。
4. 编辑器接入导入预览、字段确认、诊断和导出入口；失败时保留可修复草稿。
5. 验收覆盖恶意 URL、超限媒体、解析失败、重复导入、无权导出和资源缺失；导出包可离线阅读和重新导入。

### 12.6 迭代 4：结构化搜索与标签

**开始前冻结：** 字段权重、分页上限、索引方案、标签长度/数量上限和频率限制。

1. 基于统一可见性查询实现标题、摘要、作者、频道、合集和标签的 AND 搜索；按相关性及更新时间衰减排序，不做正文全文或语义搜索。
2. 增加作者标签、公共用户标签和规范化搜索键模型/索引；作者标签保留顺序，公共标签按使用次数及最近使用时间排序。
3. 实现添加、撤回及作者/管理员移除 API，并原子校验登录态、数量、重复值和频率。
4. 在编辑器、文章详情和搜索页接入标签管理和筛选，不建设标签聚合页或标签关注。
5. 验收：无权内容零泄露；标签规范化、频率限制、撤回权限、排序稳定性和跨页分页均有测试。

### 12.7 迭代 5：内容治理

**开始前冻结：** 举报频率参数、管理员队列分页/审计字段和作者申诉呈现方式。

1. 建立文章、评论和公共标签的统一举报目标与审计模型，使用固定理由枚举并要求“其他”填写说明。
2. 实现单用户单有效举报、频率限制、7 天内 3 位用户阈值、自动隐藏和待复核状态；目标可见性和复核记录在同一事务更新。
3. 提供作者一次申诉、管理员恢复或归档、结果反馈 API，且不暴露举报者或其他举报细节。
4. 在对应详情和管理界面接入举报、待复核、申诉与处理流程，复用现有管理权限体系。
5. 验收覆盖重复/恶意举报、阈值边界、实质修改、作者编辑限制、驳回与可见性恢复。

### 12.8 迭代 6：个性化推荐

**开始前冻结：** 信号权重、时间衰减、热度窗口、冷启动比例和 90 天清理频率。

1. 规范订阅、点赞、收藏、稍后阅读、关注频道、打开文章、阅读进度和完成阅读事件，确保不记录无权内容。
2. 建立 90 天特征查询和账号删除清理路径；候选必须先经过统一可见性过滤，再计算排序。
3. 实现账号级个性化开关、清除画像、关闭后的时间顺序回退和新用户的新鲜度/热度混合。
4. 推荐页接入开关和稳定分页游标，不增加推荐理由、邮件或站内通知。
5. 验收覆盖开关、清除、冷启动、跨设备同步、权限过滤和分页稳定性。

### 12.9 迭代 7：RSS 分发

1. 定义作者、频道、合集三类公开 RSS 路由，每条查询复用统一公开可见性判断。
2. 输出完整正文、绝对媒体 URL、稳定 GUID 和更新时间；修改只更新条目，归档后从后续 feed 移除。
3. 增加作者/频道 RSS 开关、缓存和限流；对 XML、CDATA、HTML、Unicode 和 URL 进行安全转义/清洗。
4. 验收覆盖 RSS 校验、特殊字符、媒体、归档、可见性、GUID 稳定性、开关、缓存和限流。

- 覆盖正常流程、权限拒绝、并发或重试（适用时）及失败恢复的自动化测试。
- Frontend 桌面/移动关键流程验证记录，以及 Backend 构建和受影响测试结果。
