# Papers AI audit and rollback

This release reuses the existing append-only application audit table and immutable file versions. No database migration is needed.

- After authentication, explicit consent, input validation and admission, model requests append a server-issued attempt identifier. Successful proposals and best-effort terminal failures append events. An interrupted server process or unavailable database may leave a start event without a terminal event. Rejected requests before admission are not model attempts.
- The project proposal response contains a server-generated proposal ID. The existing file management transaction supports ai_apply with that ID, the reviewed replacement contents and expected project/file revisions. It verifies all selected file IDs, before/after content hashes and exact saved revisions against the attested proposal. Actual committed revisions and the application event are written atomically. A stale proposal or tampered content cannot be accepted through this route. Ordinary file edits remain ordinary edits; single-file local and CRDT acceptances are not attested AI writes.
- ai_rollback accepts an applied event ID and current project revision, never arbitrary replacement contents. The transaction reads immutable history and verifies that each affected file is still at the exact applied revision, path and content. It restores all affected files as new versions, or none. Unrelated later changes are preserved. Normal structural writes may invalidate existing collaborative epochs; the UI warns about that. Repeated rollbacks and subsequent edits to any affected file are rejected.
- The owner-only activity endpoint shows the latest 50 events, associated attempt IDs and revisions, accepted file IDs and bounded token counts. No raw model prompt, response, manuscript content, filename, provider URL, key or error message is persisted in audit metadata. The regular version history continues to preserve accepted source.
- The existing audit table provides application-level append-only history, not a cryptographic or administrator-proof ledger. No synthetic AI user or autonomous write access is introduced. Requests and accepted project plans are associated with the authenticated human owner.

Live provider acceptance must use an authorized test key and synthetic non-confidential source. Do not exercise audit rollback on production user manuscripts for smoke testing.
