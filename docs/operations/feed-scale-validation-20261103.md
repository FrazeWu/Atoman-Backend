# Feed 去重投影：隔离规模 / 并发性能验收记录（2026-11-03）

## 范围与安全门禁

- 隔离专用分支 `test/feed-scale-validation-20261103`，基于 `ac3480c`；不接入生产 API/Worker，不执行生产 DDL，不改动 NAS 备份。
- 明确由 `scripts/test-feed-scale-isolated.sh COUNT` 启用，COUNT 限定为 10,000 / 100,000 / 360,000；使用唯一命名、运行后自动销毁的 PostgreSQL 16 容器及单独 `*_test` 数据库，拒绝继承数据库 DSN。
- PostgreSQL 容器 CPU 限 1.5、内存限 1536 MiB、禁用 swap；Go 测试使用 cgroup v2 临时 Scope 限 CPU 150%、内存 2200 MB、禁用 swap，Go `GOMAXPROCS=2`、`GOMEMLIMIT=1250MiB`、`GOGC=75`。总执行时间上限 14 分钟。每 25,000 条验证数据库大小不超过 1.9 GiB；Docker 容器临时数据随任务结束删除。该数据库大小保护是分段检测，不是操作系统硬性磁盘配额。
- 数据完全合成：1 万对应 40 个 RSS 来源，10 万/36 万对应 80 个来源；相邻 24 秒分布跨度，约每 12 条有一条跨来源 URL/标题重复；5% 有较长全文。基准覆盖分页、最新增量、8 源并发写入、刷新冷却期与日志保留。不包含真实用户数据、部署过滤、真实全文分布及大量高相似标题。

以上延迟取 25 次串行读取的排序第 24 个为 P95（从 1 计数）。写入使用 8 个互不相同的来源、每个 4 条批量 INSERT 语句（每语句 4 篇）。10k 的写入 P95 为 79.17 ms；100k 的 P95 为 64.15 ms；360k 的 P95 为 66.44 ms（p50 20.69 ms）。每轮过期快照严格拒绝读取、复杂多源变更在重建冷却期内保持失效，避免输出错误结果。PostgreSQL `EXPLAIN (ANALYZE, BUFFERS)` 检验深分页为 `feed_dedup_snapshot_rows_pkey` 索引扫描；360k 深分页 SQL 本身约 0.148 ms，但含版本验证、文章读取、ORM 映射的完整读取 P95 为 17.10 ms。

## 360k 资源与扩展性结论

- 隔离测试全链路成功，`go test` 退出码 0；构建后 `feed_items` 总表及索引约 207.5 MB，投影代表行及索引约 98.0 MB，原始成员索引约 186.2 MB，数据库整体约 502.2 MB。按当前模拟分布，每保留一个额外完整历史投影代可能多占用约 284 MB（不含其他表的影响），故旧代清理需遵守读取 grace window 并防止无限累积。
- 360k 构建 Go 累计分配约 12,339 MiB（多次分配之和），构建后活跃堆约 269 MiB，Go 进程 `VmHWM` 约 1,280,000 KiB（约 1.22 GiB）。**累计分配不能直接等同于内存峰值**。当前服务器内存 7.8 GiB，测试已设置 2.2 GB 的进程上限。
- 360k 构建 88.5 秒，已接近当前测试分支刷新 Worker 默认的 120 秒单次超时；在源分布更密集、机器负载更重或重复更复杂时，可能触发超时。需要在生产数据脱敏副本上选取真实资源预算、优化完整构建并设置重试退避和防风暴保护，不能盲目加大超时。
- 从 100k 到 360k，数据增加 3.6 倍，全量构建时间从 18.55 秒增至 88.48 秒（约 4.77 倍），需要重点分析聚类成本、内存分配和 PostgreSQL 大批量插入，不能假定线性扩展。
- 隔离容器退出时会销毁其临时数据库。没有从生产拷贝用户内容或执行任何生产迁移；完整数据经旧算法的每页等价性仅在小型专项样本对照，360k 只验证合成集的明确去重数量、前插及分页。

## 上线前仍需

1. 对生产库**脱敏、经授权的只读副本**重复接近真实分布的全路径测试（含密集转载、长正文、NULL 时间、已读/订阅/搜索/热门/混排）；当前投影并未覆盖这些查询。
2. 在隔离副本测量 RSS 大批量事务触发器耗时、同源串行锁争用、跨源锁竞争、失效期间旧查询 API P95、全量重建多代存储增长以及安全 GC 时间。
3. 完成版本触发器/投影索引的上线与回滚迁移、独立 Worker、容量限额、异常告警、灰度开关，以及明确的完整重建预算；禁用所有自动生产清理直到审计完成。
4. 单次测试的 P95 为串行样本，不代表并发客户端 API 延迟，硬件和容器限额与真实生产不同。
