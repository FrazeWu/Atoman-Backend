# Feed 36 万条全量构建：CPU 分段定位与无损滚动锚点优化（2026-11-04）

## 操作范围

- 独立分支 `perf/feed-rebuild-profile-20261104` 从 `perf/feed-hot-title-guard-20261103` (`697d6e6`) 分出，未合并、推送、注册 Worker 或执行生产 DDL；生产 `main`、API 和 NAS 未修改。
- 所有压力测试使用已有受限脚本 `scripts/test-feed-scale-isolated.sh`：临时 PostgreSQL 16、CPU 1.5 核、DB 内存 1.5 GiB，Go 进程 2.2 GB，测试任务 14 分钟上限，测试数据库强制 `_test`、生成数据全部是模拟内容。
- 测试时通过显式 `FEED_SNAPSHOT_STAGE_TRACE=yes` 记录加载/去重/组装/写入时间，通过 `FEED_SCALE_CPU_PROFILE=yes` 输出仅供诊断的 Go CPU profile 到 `/tmp`。两开关默认关闭；它们不属于生产接口、迁移、Worker 或读取开关。

## CPU 采样分析：问题集中在字符串候选键

在 100k `prodshape` 模拟样本中，原版首次构建约 42.04 s：加载 11.02 s、标题去重 17.03 s、组装 0.90 s、事务写入 13.08 s（代表项 5.42 s、全成员 7.64 s）。CPU profile 中 `runtime.mapaccess1_faststr` 累计约 13.54 s，Go string-map hash/matching 的底层 `internal/runtime/maps.ctrlGroup.matchH2` 平坦采样占比约 21%；`duplicateGroupIndex.firstMatch` 累计约 20.38 s。该分析受 CPU profile、缓存冷热和其他并发任务影响，不是生产 SLA。

此前索引为每篇标题生成大量 4/6/8 rune 子串、反复转换短字符串、通过 `map[string]` 查询不同锚点。新实现把内部模糊/子串键改为 `map[uint64]`，通过固定宽度 rune 多项式哈希及滑动窗口 O(1) 更新；建索引和检索使用完全相同的哈希算法。哈希碰撞只会把额外组加入候选，**不会删掉候选**；最终始终调用原有 `group.matches`，按 groupID 升序保留首个匹配组，URL 全局精确匹配、72h 时间/零日期、0.9 相似度、子串包含及来源成员语义均不修改。

新增 `duplicate_index_rolling_anchor_test.go`：25,000 个随机 Unicode/多语言/Emoji 窗口组合，3 种宽度的滚动哈希与直接计算逐位一致，覆盖重复短语与极短标题；保留既有候选不漏检与线性参考差分测试。

## 未解除的上线阻断条件

1. 基线与优化版本没有进行多组完全配对交叉测试，负载和缓存变化可达几十秒；不能直接声称最终生产中稳定加速 2～3 倍。
2. 内部 Go 去重索引的哈希碰撞不改变语义这一条件已通过代码审查和随机差分验证，但尚缺全部真实数据及完整 HTTP/订阅/搜索/混合博客/已读/热门/随机查询的等价验收。
3. 360k 首次全量数据库写入仍约 28 s，第二次约 34 s，当前每批插入 350 条代表项与 300 条成员。下一阶段应在隔离副本比较 350/300 与更大安全批次，核对 PG 参数限制、事务内存、数据库 WAL 与回滚；禁止直接在生产改写入策略。
4. 生产迁移与回滚、独立 Worker 入口、灰度/回退 feature flag、监控告警、旧 generation 存储持续增长与备份恢复演练未完成。**当前结论仍为 NO-GO 生产部署。**
