# Feed 热点标题：保守的 Bigram 位图筛选（2026-11-03）

## 工作隔离与目的

- 分支 `perf/feed-hot-title-guard-20261103`，基于 `5aa66bf`（高频锚点 UTC 日期桶、36 万条隔离测试）。仅实验 worktree。没有更新生产代码、数据库触发器、HTTP 读取路径、Worker、生产迁移及 NAS。
- 原有日期桶能降低跨年份共享标题短语产生的无意义候选，但是在同一 72 小时窗口内高度重合的短语仍可产生近乎二次方的候选遍历。原始 10k 全共享短语压力场景构建约 52–58 秒。
- 本次仅增加 **候选必要条件预筛**，不改变去重判定函数 `group.matches`。URL 去重全局无时间窗，完全绕过预筛。其他候选继续使用原来的 URL 标准化、标题标准化、72 小时/零日期、0.9 Levenshtein 相似度、>=18 rune 的精确子串、最早匹配组、源名称及成员 ID 规则。

## 无漏报剪枝的依据

- 只有候选数达到 **128**，且至少占该时间窗口内已有代表项的 **50%** 时，才按需为新文章和对应代表项生成相邻 rune 二元组（bigram）位图，四个 64 位 bitset；代表项的位图在当次扫描中懒加载缓存。低于阈值或者窗口内候选比例较低时走原匹配路径；日期窗口使用已有的 72 小时和零日期语义，只需要累计每天的代表项数量。**哈希特征碰撞只会导致多保留候选，不会错误排除**。
- 当编辑距离 `d <= k`，单次插入、删除或替换最多破坏任一方向两个相邻 bigram，所以两串任一方向的独有位图特征数 `<= 2k`。采用 `k=ceil((1-0.9)*maxRuneLength)` 的宽松上界（最终判断仍是原浮点条件），若位图差异超过此值，可以确信标题相似度不达标。
- 精确子串规则独立于编辑距离：长度 >=18 rune 的较短标题确实被包含于较长标题时，较短标题的所有 bigram 都在较长标题里。因此只有“不存在该位图包含关系”时，才能排除这条分支。
- 二者均不满足且 URL 不精确相等时，才放弃代价较大的编辑距离；最后仍执行原 `group.matches`。按 groupID 升序求第一个命中，不改变代表元选择。
- 本预筛不是等价性的形式化证明；但新差分测试包含 35,000 对 Unicode、随机编辑、短/长子串、共同前缀及长度边界，并包含 1,250 篇高相似样本对旧线性算法逐项比对。额外保留已有 30,000 次候选漏检、日桶边界、随机集合及独立 PG 集成测试。

## 性能观测

- 1 万条 `adversarial` 共用短语/961 来源模拟：最初的“所有查询都启用位图”原型首次构建 15.228 s、二次 13.499 s，但 36 万生产形态首次构建 **95.67 s**，慢于分桶基线 **71.52 s**，说明额外位图计算有普通负载回归风险。因此未保留该原型，改成仅热点启用位图。
- 密度门禁版在 10k 全共享短语下首次 **13.998 s**、二次 **16.514 s**，去重后 **9,167** 个代表项，Go RSS 峰值 **83,588 KiB**，首页 P95 **7.67 ms**、深分页 P95 **6.10 ms**；同源/多源写入和旧代清理均通过。隔离 PostgreSQL CPU 1.5、内存 1.5 GiB，Go CPU 1.5、内存 2.2 GB，容器正常退出并清理。

## 仍然阻断生产部署

1. **性能门禁未解除：** 生产形态 360k 测试中，密度门禁版比同机基线慢约 3%/7.5%；需要多次交叉顺序对照、Go CPU profile 与真实相似度分布，进一步降低高相似标题成本而不增加普通文章查询成本。不要用单次测量宣称非回退。
2. **超时与空间：** 完整构建仍可达约 100 s，接近 Worker 120 s 预算，且保留新旧双代可能占用额外约 280–300 MB；日志与历史代维护需证明不会引起长期 bloat/锁阻塞。
3. **接口契约：** 只证明算法索引剪枝的必要条件与部分 RSS-only/recent 对照。搜索、订阅、混合博客、已读、热门/随机等 API 未覆盖，不能开启全站投影读取。
4. **运行与迁移：** 生产迁移/回滚、独立 Worker 发布入口、灰度 feature flag、真实备份恢复演练与故障指标均未放行；所有实验代码仍只在独立分支。
