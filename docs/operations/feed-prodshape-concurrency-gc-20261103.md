# Feed 上线前：生产聚合分布驱动的隔离验证（2026-11-03）

## 工作隔离、源数据边界

- 此验证位于 `test/feed-prodshape-concurrency-gc-20261103` 分支，继承 `86c4fa6`，未发布 API，未对生产执行数据写入、DDL 或压力测试，也未处理真实文章正文或复制任何用户记录。
- 对本机生产 PostgreSQL `atoman_prod` 只读执行 `pg_class` 近似计数和 `TABLESAMPLE SYSTEM (1.5) REPEATABLE(42)` 的汇总查询；连接开启 `default_transaction_read_only=on`，SQL 使用 `BEGIN READ ONLY`，每条语句 6 秒上限。连接机密未打印或保存到测试资产。
- 生产元数据：`feed_items` 统计估计约 **361,080 行**（`reltuples`），可见 `external_rss` 来源 **961** 个。样本 **5,110 行**、其中未软删除约 **4,999 行**，平均标题长度 **47.9**、P95 **103**，平均链接长度 **58**，`full_text_html` 超过 500 字符约 **20.4%**，`reader_html` 超过 500 字符约 **55.6%**；样本内规范化 URL 粗去重后重复 **404/4,999 ≈8.1%**（仅字符串粗去重，非实际去重规则）。抽样有 332 个来源有文章，最大单来源 378 行（约 7.6%），体现明显的长尾分布。采样为按数据页抽样，并非严格随机行抽样，所有占比仅用于压力样本设计，不代表完整生产统计。
- 合成压力样本采用 **961 来源**、一个约 7.7% 的头部来源、若干中等来源与长尾来源、8.3% URL 重复、标题长度约 53/100+ 字符、20% 较长全文、56% 较长 reader HTML、部分 2012–2026 的发布时间；**只由确定性伪造数据生成**，不包含生产实际文字、URL 或私密元数据。
- 执行脚本 `scripts/test-feed-prodshape-isolated.sh {10000|100000|360000}` 调用专用 PostgreSQL 16 临时容器（CPU 1.5 核，内存 1.5 GiB，禁 swap）、Go 临时 systemd scope（CPU 1.5 核，内存 2.2 GB，禁 swap）；每个完整测试上限 14 分钟。用例只对独立 `*_test` 数据库写入，容器结束自动回收。

- 与上一轮随机标题 10k 全量构建约 1.33 秒相比，所有标题共享长短语时耗时超过 50 秒、累计分配约 22,602 MiB。**该极端场景暴露出候选去重索引的高频短语性能劣化，不能据此认定 36 万条真实标题可在 120 秒内完成构建。** 该场景只允许 10k 测试，禁止扩展到 36 万条以免形成无意义的昂贵负载。正常生产形态样本设置 5% 共享短语，其余高区分度标题；仅匹配抽样边际统计，并不代表真实文本的模糊相似度分布。
- 同源压力：8 个写入者、每人 4 次语句，每条语句 4 篇，总 32 语句/128 篇，不应丢失日志或跨源版本；多源基准同时覆盖 8 个不同来源。加测了同源事务互斥和跨源不被锁住的显式并发单测。
- 旧快照回收通过模拟退役超过 1 小时的旧 generation 验证，确保投影代表行和所有原始成员行均被清除、新活动 generation 不受影响。**行删除并不立刻释放数据库文件空间**，后续需评估 PostgreSQL WAL、MVCC/VACUUM、历史代上限和长期 bloat。

## 发布门禁（尚未解除）

1. **高相似标题**：进一步在授权的脱敏生产副本上按真实重复/标题分布重测，并对候选集合过载优化，提供与旧算法一一等价的证明和压力数据。
2. **超时与资源**：真实规模构建已接近刷新 Worker 默认 120 秒预算；必须设置隔离 Worker CPU/内存/时间、冷却期、重试与告警，且所有快照读取异常均回退原查询。
3. **数据契约**：RSS-only/recent/无筛选只是有限范围；博客混排、订阅、已读、语言、搜索、热门/随机、过滤等查询路径未完成逐路径等价验收，禁止直接开启全站投影读取。
4. **迁移与回滚**：触发器、版本日志、投影结构、索引与初始化构建的正式迁移文件、反向操作、线上备份检查和停机回退方案尚未审查；不能在生产执行实验性 DDL。
5. **回收与锁**：并发长事务/更高并发数据库锁、旧代回收与查询竞争及回收后空间复用需要长期监测；本阶段仅是短时间合成测试，不能等同生产吞吐能力。

## 高频标题锚点索引优化：独立分支复测（2026-11-03）

**分支** `perf/feed-anchor-day-buckets-20261103`；实现提交 `f34b390`，合并同一数据形态基准 `568437e` 后复测。仍未进入 `main`，未推送、未执行生产迁移或 Worker。

### 设计及语义证明

- 只有命中超过 **96** 次的模糊标题/子串锚点候选列表，才从紧凑数组转换为 UTC 日期桶。低频锚点维持既有实现；URL 全局精确匹配仍不受任何时间窗口限制。
- 非零发布时间的标题匹配只接受彼此相差最多 72 小时：读取时只查询 UTC 日桶 `[date-72h,date+72h]`；包含边界日期，由旧的 `group.matches` 再做精确时间与标题比对。
- Go 零时间戳是旧规则特殊值，可与任意时间匹配；因此单独保留跨日期通用桶，若查询自身零时间则查询全部桶，避免遗漏。
- 所有候选最终按原 `groupID` 升序排序，严格保持原来的**首个匹配组优先**规则。没有修改 URL/标题标准化、72h/0.9 阈值、子串包含、重复源和成员 ID 语义。
- 新增热锚点和 72 小时边界/零日期/Unicode/负 Unix 日的等价性测试；原有 30,000 次随机编辑距离/子串候选不漏检测试也已通过。该证明只覆盖索引剪枝条件，不能代替完整 API 端到端契约验收。

### 仍须审查

- 71–74 秒隔离构建低于 Worker 当前默认 120 秒超时，但没有覆盖真实中文/英文复杂标题、突发海量热点文章与高并发 RSS，**不能直接提升为生产 SLO**。
- 如果大量标题在同一 72h 窗口内都包含同一短语，日期桶无法减少该窗口内部的候选数量；10k 全共享短语的原版构建仍约 52.6 秒，属于尚未消除的极端热点风险。
- 生产迁移、独立 Worker、异常回退日志/指标、只针对 RSS-only/recent 的灰度读取开关、旧代自动回收和完整接口等价测试尚未落实。**此阶段仍不部署生产。**
