# AToMAN 后端系统性重构计划（2026-11-03）

## 目标与约束

- 在 Go/Gin/GORM/PostgreSQL 模块化单体架构内渐进重构；不为了拆分而引入微服务。
- 保留现有 API 路由、响应格式、权限、分页、排序与去重行为。
- 所有修改在独立 worktree 和分支进行；生产数据库只读审计，测试数据库必须独立。
- 发布 API 和音乐导入 Worker 时保持同一版本，保留旧版回滚；数据库迁移必须前后兼容。
- NAS 生产库自动备份链路独立运行，不依赖 Mac，不纳入代码重构范围。

## 审计基线

- 起点提交：`e01ab0b`；Go 代码约 1,155 个文件，包含自动生成 Swagger 与测试代码。
- 文档记录约 502 个路径、650 个 HTTP 操作；模块与旧 `internal/handlers` 并存。
- 生产数据库 `atoman_prod` 约 6.3 GB，`public.feed_items` 约 36 万条记录，表及索引等约 4.5 GB。
- `feed_items` 的全文、reader HTML 等大字段原先会随去重全量查询一起加载。
- 在生产库观察到 165 个 `test_*` schema；须调查来源，不可未经确认批量清理。
- API 同进程运行 RSS、全文提取、书籍处理、索引通知和清理等任务，音乐导入单独有 Worker。
- 基线 Go 编译和 vet 通过（VPS Git VCS stamping 失败时使用 `-buildvcs=false`）。

## 阶段 A：Feed 首批安全修复（当前任务分支）

1. **测试库保护**：显式测试 DSN 只能连接专用 `*_test` 数据库；脚本和 Go `testdb` 双层校验。拒绝生产库/开发库 DSN；不清理现有 schema。
2. **去重候选索引**：不改变原去重匹配规则与优先顺序。小分组使用原顺序扫描，大分组才建立候选索引；通过新旧实现对照测试。
3. **瘦字段查询**：对无全文搜索的常见去重查询，仅检索 ID、标题、URL、日期、类型、来源等字段，页面选定后再查完整文章。搜索、热门排序等特殊路径暂沿用原逻辑。
4. **已读状态**：候选量大时按用户取已读 ID 并求交集，避免超大 `IN` 参数列表。
5. **回归测试**：同一快照内比较排序、分页、重复项元数据、已读状态、全文响应和公开/订阅/探索路径。

当前阶段 A 不等于实现了全量数据库级分页：大规模去重仍需扫描元数据；只减少全文读取、改善分组检索和已读查询。此限制必须保留在验收记录中。

## 阶段 B：Feed 真正的数据库级分页（P0，后续独立任务）

- 用可重现测试构造 1 万、10 万和接近生产规模的模拟订阅文章，记录 SQL 条数、返回行数、P50/P95、峰值内存；严禁对生产库进行大规模压力测试。
- 为去重建立可复用的轻量簇索引或结果物化方案，明确新增文章、删除、来源隐藏、跨来源重复与修订时的更新规则。
- 保持模糊标题、72 小时窗口和 URL 标准化规则，证明跨页总数及代表项一致；不允许通过硬截断产生错误的总数。
- 完成公开 Feed、探索页的搜索/热门排序、订阅混合流、订阅中心全部路径的有界查询；优先使用数据库游标/keyset 分页。
- 补充分页与聚合的 EXPLAIN (ANALYZE, BUFFERS) 测试，并在隔离环境确认性能；生产仅只读采样。

## 阶段 C：音乐（P1）

- 拆分导入解析、状态机、对象存储提升、事务提交、修订及通知的职责。
- 用幂等键、受控重试、持久任务/补偿避免 R2 与 PostgreSQL 事务不一致。
- 覆盖重复提交、并发编辑、音频文件失败、Worker 重启、回滚与归档。

## 阶段 D：书籍与 Wiki 修订（P1）

- 明确作品、版本、电子文件、阅读进度、公共 Wiki 修订及合并重定向边界。
- 不改变既有语言社区默认版本、用户权限及历史可追溯要求。

## 阶段 E：平台能力（P1-P2）

- 在独立事务/版本控制体系下治理数据库迁移，避免长期重跑非幂等数据回填。
- 将 API 进程中的后台任务改为受控调度与租约式执行，确保单实例和多实例均不会重复处理。
- 收紧跨模块 import，集中配置与外部依赖，逐步退出旧 `handlers/service` 混合结构。
- 增加 PostgreSQL 慢 SQL 观测（预先评估开启代价）、任务失败告警、API 延迟及内存监控。

## 每个阶段发布门槛

1. 创建独立 worktree，运行 `codegraph init`，确认 main 无未提交变更。
2. 在隔离 PostgreSQL 中执行目标模块测试，运行 `go build ./...`、`go vet ./...`、脚本与 Swagger 契约校验。
3. 记录基线与修改后性能、内存、SQL；关键语义没有回归。
4. 检查 Git diff、迁移可回滚性及生产配置差异；避免 API 和 Worker 版本不一致。
5. 集成前审查；生产部署后验证健康、关键用户路径与错误率；异常立即回滚二进制版本。

## 不执行的操作

- 不对现有生产库测试 schema 做清理或删除。
- 不在生产库上执行基准压测，也不在当前阶段修改生产数据库 schema。
- 不删除现有备份、不依赖 Mac 执行备份、不改动现有 NAS 定时配置。
- 不能在 Feed 全路径的性能与语义验收前宣称 P0 重构完成。

## 阶段 B 研发记录：数据库去重投影原型（2026-11-03）

**实现位置：** `internal/modules/feed/dedup_snapshot*.go` 和 `internal/service/duplicate_{index,similarity_fast}.go`。

**当前能力：**
- 为 public/recent/无筛选的 Feed 数据建立离线去重投影，严格沿用按时间倒序及先命中组优先的 URL/标题去重算法。
- 结果写入按 generation 区分的 PostgreSQL 行表；页查询以 `(generation_id, position)` 范围扫描，精确返回投影总数，最后才补齐文章全文。
- 投影发布通过事务原子切换 active generation；旧代暂时保留，避免并发阅读中途失效。
- 测试用事务版本标记对新增、删除、修改标题/链接/作者/时间/源关联、来源隐藏等事件进行失效处理；普通全文丰富化不触发重建。读操作在 `REPEATABLE READ` 下核对一致版本。
- 旧代清理函数具备 >=1 小时安全窗口及避免误删当前活跃 generation 的保护，但**未设置生产自动清理任务**。
- 低于128个代表组时维持线性查找；大于此数量使用 4/6-rune 模糊匹配锚点、8-rune 字符串包含锚点。通过与原算法的随机、Unicode、编辑距离和大于阈值样本的等价性测试。

**隔离性能（100,000篇合成独立文章，2 Go CPU）：**
- 最初短锚点方案：快照重建约70.03秒，Go 累计分配约15.8GiB。
- 加长候选锚点并使用限制编辑距离 DP：重建约9.12秒，累计分配约2.1GiB。
- 第9999页、10条/页，20次串行读取 P50 6.43ms、P95 7.02ms；EXPLAIN 显示投影表通过主键索引扫描。
- 对 10,000 篇合成文章：最后一轮重建约0.86秒，深分页 P95约7.8ms。
- **以上不是生产吞吐量数据，也不代表线上请求端到端延迟。** 模拟标题较为独立，需额外测试高度相似标题、多源重复、长正文等真实分布。

**未达到上线条件的事项：**
1. 当前 `feed_dedup_revisions` 的触发器只在隔离测试环境安装，没有注册到生产迁移。共享事务性版本行存在写锁竞争或死锁风险，上线前需在独立生产数据副本上验证并考虑分片版本/事件日志方案。
2. 尚未实现稳定的自动刷新任务、增量更新与异常回退调度。每次重新构建扫描所有候选元数据，不允许按每次 RSS 更新全量重建。
3. 快照读函数暂未接入 Gin 路由，普通调用链仍走上阶段的轻量扫描逻辑。必须先建立数据变更 CDC/版本检查闭环，才能考虑用它替换响应路径。
4. 当前投影只覆盖 public/recent/无筛选的外部 Feed 候选结果；混合博客文章、站内订阅、已读聚合筛选、搜索、热门排序、随机排序、隐藏源和来源子集等尚需等价性验证。不得通过提前 LIMIT 或硬截断改变总数、代表项或分页顺序。
5. 旧代快照会持续占用空间，必须在完成安全的回收调度之后上线；确认事务读者使用 `REPEATABLE READ`，并保留 grace 期。
6. 最终必须在隔离数据库中完成接近36万条文章规模的性能与资源上限验证，确认测试用容器有 CPU、内存和磁盘限制，并检查生产索引策略。

**发布门禁：** 本阶段原型只提交到 `refactor/feed-db-pagination-20261103`，不进入 `main`，不部署，不对生产执行 DDL、不注册迁移、不启用触发器。保留上阶段稳定分支作为回滚起点。

## 阶段 B 下一步：按源记录版本与安全自动刷新原型（2026-11-03）

本批次工作保留于 `refactor/feed-refresh-20261103`，不修改生产数据库、不启用线上 API。

### 已实现及已验证的能力

- **按源版本台账** `feed_dedup_source_revisions`：每个 RSS 源拥有独立且事务性的版本号，读路径使用 `SUM(revision)` 作为全局失效标记，避免上版所有写入争用单个全局版本行。
- **语句级变更触发器**：针对 `feed_items` 与 `feed_sources` 的 INSERT、UPDATE、DELETE、TRUNCATE 共八种事件。对批量变更，一条语句每个相关源只提升一次版本；比较旧/新值，无关的全文丰富化或幂等 UPDATE 不产生失效；跨源移动同时记录两边；TRUNCATE 通过保留的全局哨兵失效。
- **事务性变更日志** `feed_dedup_change_events`：逐来源、逐版本保存事件类型和本语句中变更的文章 ID 数组。增量处理可以从某个来源版本精确读取后续事件，不依赖可能乱序的非事务序列号或时间戳。日志和版本号在同一事务写入，回滚时一起撤销。
- **刷新协调器**：只有发现版本过期且已过 quiet period 才执行；通过 PostgreSQL 会话级 advisory lock 防止多个 Worker 同时重建；重检防止锁等待期间重复工作。只提供独立 Worker 可调用的原型 API，尚未从 `start_server`、Worker 或 HTTP 路由注册。
- **受控失效**：在 REPEATABLE READ 事务中获取当前来源版本并读取投影页；只要版本不一致，返回 `ErrDedupSnapshotStale`，禁止返回未验证的新旧混合结果。
- **安全门禁**：实验性 SQL 触发器安装函数必须在 `test_` 开头的独立测试 schema 才可运行，否则在任何 DDL 操作之前拒绝。
- **专项契约对照**：公开 Feed 与探索 Feed 在“仅外部 RSS、recent、无额外筛选”的受控数据集中，页序、总数、重复分组、正文读取与投影一致。其余请求形态尚未通过此项验证。

### 尚未完成 / 不允许提前上线

1. **真正的增量投影变更**仍未实现。当前 journal 仅提供增量识别所需的可追溯事件；刷新器将多次变更合并为一次全量重建。未来必须记录每代的逐来源版本检查点，再对 insert-only/append-only 等可证明正确的事件尝试局部构建；对更新、删除、来源隐藏、跨来源或模糊匹配导致的代表项变化，安全退回全量重建。不能默默丢弃重复成员或错误计算总数。
2. **生产触发器尚未迁移**：语句级触发器须在独立生产数据副本上评估写入放大、每来源锁争用、版本求和扫描、长事务和重复提交行为；需要完整迁移/撤销脚本和上线窗。
3. **变更日志与快照代清理**尚未启用。未来须保证每个活跃快照都能从其版本检查点向前回放，不得早于该检查点裁剪日志。
4. **API 支持范围**目前仅经过 RSS-only/recent 受控对照。公开/探索流中的博客混排、搜索、热门/随机排序、订阅混合流、已读状态、来源/语言/分类筛选都必须分别进行接口等价性验证，缺一项就不能切换对应入口。
5. **自动刷新部署**目前未开启，不能把实验性 Worker 接到 HTTP 进程。生产部署前须设置单独 Worker、限频与资源预算、错误告警、失效时降级路径、发布开关和快速回滚。
6. **性能基准更新**：上一版的 10万条构建9.12秒、P95约7.02毫秒只是改造前的隔离基线；新增加的触发器及 journal 需要独立的批量写入基准评估，不能沿用作为新版本生产指标。

## 阶段 B 局部增量投影：严格守卫的历史文章补录（2026-11-03）

分支：`refactor/feed-incremental-20261103`（基于 `fe28daf`）。本阶段仍是独立测试原型，没有新增正式迁移，也没有接入现有 API 或自动启动 Worker。

### 已实现

- 快照头增加**按来源的事务版本检查点**，并保存原数据的最末文章排序键 `(published_at, id)`。投影行保存首个代表项的规范化 URL/标题，避免在后续安全更新时重新读取原始所有正文。
- 只允许**一条变更事件、一次单文章 INSERT、一个来源版本号恰好增长1、文章可见且按数据库全序排在此前最旧文章之后**的情况进行局部增量更新。其他事件统一退回全量重建，不基于时间戳猜测事件顺序。UUID 相同发布时间的排序关系也必须严格一致。
- 新文章与先前所有代表分组的去重判定复用 `internal/service` 中的原始 `group.matches`；标题匹配在72小时范围内，规范化 URL 相同则不受时间窗口约束。零日期按原算法允许标题匹配任何时间。
- 若不匹配已有组，直接按尾部位置新增一条投影记录；若匹配已有组，只更新原代表项的 `duplicate_count`、成员 ID 及排序去重后的来源名称。不调整之前任何代表项的顺序。投影行、快照头和来源版本检查点全部在同一 `REPEATABLE READ` 事务更新。
- 普通读取仍通过 `REPEATABLE READ` 验证版本号；异步 RSS 并发写入可令现存快照过期，旧结果不会在新的事务中被错误当作最新结果。
- 新增测试覆盖唯一历史文章、URL 重复（即使超出72小时）、模糊标题重复、跨来源重复、同一时间戳 UUID 全序、连续两次增量、空投影、非增量场景回退，以及与完整原算法逐页比较。

### 隔离性能（10,000篇随机标题、单来源、10,000秒分布）

- 完整构建并写入追踪：`783ms`；一篇紧邻历史尾部的新增文章：`135ms`（过程累计 Go 分配约20.3MiB）。
- 一篇比历史尾部早100小时的新增文章：`42ms`。两种尾部补录分别约快5.8倍与18.8倍。
- 数据只反映此隔离样本，不包括真实 RSS 文章的密集同标题、长期 URL 重复、网络或多源写入竞争，不能作为生产 SLA。

### 明确不适用与待办

1. **最新文章通常插在排序前端，当前仍触发全量重建。** 因为原去重算法是从最新到最旧贪心分组，新代表项可能改变后面许多文章的分组，不能只在投影前端添加一行就宣称正确。
2. 多条 INSERT、修改、软/硬删除、订阅源隐藏或标题变动一律回退完整重建；暂未实现可证明正确的新文章前插或批量增量。
3. 目前新的投影行增加字段，生产迁移要处理旧头行的 NULL/default、索引和历史代兼容问题；本分支绝不能直接修改生产 schema。
4. 新增代表匹配过滤在同一72小时窗口候选密集时可能仍需要读取很多投影行；只有通过36万条接近生产分布测试及并发写入测量，才能判断稳定性能。
5. `readPublicRecentDedupSnapshotPageTracked` 仍不是现有 Gin 路由默认实现；其他支持范围、真实混排、搜索/热门、已读/订阅筛选及降级路径未完成全路径对照，不得部署。
6. 对于准备上线的刷新器，还必须评估频繁失效导致的反复全量构建，并加入独立 Worker 限频/退避/资源预算和失败指标。

## 阶段 B：最新文章前插与单来源批量增量原型（2026-11-03）

- **分支**：`refactor/feed-prefix-20261103`，继承 `28587a7`，仍未合并 `main`，未执行生产 DDL，也未注册 HTTP 或生产 Worker。
- **严格一致性证明**：旧算法是按 `(published_at DESC, id DESC)` 排序、以首匹配组为准的贪心归并。要在列表前端新增文章而保持旧分组不变，必须证明新增的每篇文章都不会匹配**任何**历史原始文章，包括曾被旧分组折叠的非代表文章。只与旧分组代表进行比较是不充分的。满足此前缀条件时，对新增批次单独调用原去重算法，原有各组的成员、代表与内部顺序均不变。
- **候选成员索引**：每个投影代增加 `feed_dedup_snapshot_members`，包含所有可见的原始文章ID、标准化标题、URL、URL SHA256、发布时间；索引 `(generation_id,published_at)` 与 `(generation_id,normalized_url_hash)`。短时窗口以72小时查询所有标题候选，URL hash 覆盖任意时间跨度的相同 URL，校验最终使用原始的 URL、模糊标题、包含子串逻辑，因此哈希冲突也不会误判为“无重复”。对旧零时间戳文章单独纳入候选；如旧最新文章的时间戳为空，保守回退全量构建。
- **资源边界**：每次单来源 SQL INSERT 最多24篇新文章；某个新项目需检查的旧文章超过25,000条、整个新增批次合计超过100,000次候选检查时，直接回退全量构建，不做静默截断。不改变原 API 返回的 total。
- **直接页定位**：快照头 `position_base` 允许负位置；前插代表项只在原始行之前放置新的负位置，不更新历史上万个旧行。当前页起始位置由 `position_base + (page-1)*page_size` 计算；尾部新增仍按当前 `position_base+total` 追加，两者能连续交替使用。
- **checkpoint 与并发**：每次刷新在 `REPEATABLE READ` 事务中锁定快照头，校验按源提交的版本/变更日志、候选成员数和新条目顺序；原子更新快照行、raw-member 索引、总数和版本。异步并发写入的其他提交会导致后续读端的版本校验失败，回退旧路径而不会静默读出过期快照。
- **批量内部重复**：同一 INSERT 语句中的多个新增文章可相互重复；原始去重算法先对新增组聚类再插入，保留来源名称、代表项、重复数量与成员顺序；新增与任一旧文章匹配则整体回退重建。
- **隔离回归**：最新独立文章、批量相互重复、跨前后增量、跨源历史重复成员、UUID 同时间排序、空/NULL 时间戳、旧元数据索引缺失、长 URL、中文标准化标题、编辑删除/隐藏源、输入超过限额，都必须用完整旧算法逐页对照，非安全前缀全量重建。
- **隔离性能基线**（Go并行度2，PostgreSQL独立容器，合成随机标题）：
  - 10,000篇、集中在近3小时：完整重建（含 raw-member 索引）约973ms，最新单篇增量约96.8ms，分配约16.4MiB。
  - 100,000篇、发布时间分散约14天：完整重建约11.58秒、Go累计分配约2687MiB；最新单篇增量约135.5ms、Go累计分配约28.9MiB。第一页和深分页已对照验证。
  - 上述数据是隔离样本，不代表生产 SLA；真实多源同题转载、RSS写入频率与突发批量更新会改变命中率和CPU开销。

### 上线前保留的门禁

1. 对超过25,000个72小时候选、跨源多事件、与旧成员匹配的前插、来源可见性变化或历史编辑，仍需完整重建；这些情况的稳定刷新吞吐和退避策略待验证。
2. `feed_dedup_snapshot_members`、快照头新列与复合索引须先作为正式迁移在独立生产数据副本执行，处理旧代字段默认值和回填逻辑。本阶段未向生产执行任何 DDL。
3. 仅检验 RSS-only、recent、无额外筛选路径的部分契约；文章/博客混排、订阅、已读、搜索、热门、随机、来源与语言筛选尚未完成切换前等价性验证。
4. 在服务真正读取投影之前，必须确保 `ErrDedupSnapshotStale` 有自动降级，刷新器具备独立部署、限频/超时、监控告警、保留代回收和异常回滚机制。
5. 生产 36万条规模真实分布、并发RSS工作负载、峰值RSS及数据库锁竞争，尚未在隔离数据副本评测。不得据此修改生产服务。

### 增量边界补充验收

- 发布时间为 `NULL` 的文章在 PostgreSQL 的 `ORDER BY published_at DESC` 中位于非 NULL 文章之前；不能用 Go `time.Time{}` 比较后错误地视为尾部新增。`tryAppendOldestDedupItem` 和安全前插均对异常零日期保守回退全量重建。
- 前插无重复文章属于当前可安全增量的场景；早期刷新单测中“任何最新插入都必须重建”的假设已修改为“新增独立文章保留代并移动位置基准”，重复或不满足证明条件时重建。
- raw-member 以标准化 URL 的 SHA256 建索引而非直接给任意长度 URL 建 BTree；完整字段仍按原去重逻辑校验，长URL不会因为索引长度限制导致发布失败。


## 阶段 B：刷新任务可靠性与异常降级护栏（2026-11-03）

- **分支**：`refactor/feed-worker-guardrails-20261103`，基于 `6506ec2`，仍为隔离原型；生产 API、自动迁移和独立 Worker 均未接入或启动。
- **限频**：在有活动快照且必须全量重建时，默认至少间隔 10 分钟；可以证明正确的最新前插或最旧尾插不受该间隔约束。冷却期间快照仍然过期，绝不错误地返回旧投影。
- **超时**：独立 Worker 每次尝试默认给 2 分钟上下文预算；持续的数据库错误不退出循环，按 2 秒起步、最多 60 秒的指数退避重新尝试，成功则重置。若发生并发版本冲突，则按正常轮询节奏重试，不作为数据库故障统计。应用层耗时函数若未检查上下文，超时只能在下一次上下文检查处生效。
- **可观测性接口**：提供 `OnAttempt` 回调，记录结果、错误、尝试耗时、连续失败次数及下次调度延迟；尚未连接统一日志、指标平台或告警器。
- **受控降级接口**：读取投影使用独立的子上下文；一旦快照过期、缺失、出错或超时，使用尚有效的父请求上下文运行调用者提供的旧查询。不允许返回部分投影，也不在客户端已取消请求时触发昂贵的旧查询。仅适用于通过完整等价性验收的 RSS-only/recent/无筛选路径，**没有在路由中启用**。
- **日志清理原型**：只有存在可解析的活动快照版本检查点，才允许回收早于至少 24 小时、且不超过该来源检查点的事件；对更新过但快照尚未处理的事件必须保留。清理在事务中锁住头记录；当前没有注册定时清理。旧 generation 回收仍保留此前至少 1 小时的安全期。
- **回归验证**：隔离 PostgreSQL 测试新增了重试/超时/退避、重建限频、正确增量不被限频、快照读取降级和保留未回放事件；上线前仍应覆盖并发数据库事务与真实业务读请求。

### 上线门禁未解除

1. 在生产库脱敏副本验证约 36 万条数据的 CPU、内存峰值、写入放大、长事务、锁争用、日志增长速度和全量重建持续时间；单次尝试上下文超时并非硬性内存限制。
2. 编写并审查生产迁移及回滚脚本，确认版本触发器与索引的增量上线策略、可恢复副本和回滚时旧路径完整可用。
3. 增加真实独立 Worker 入口、资源限额、服务管理与指标/告警连接，明确生产降级延迟与慢查询预算。
4. 混合博客、搜索、热门/随机、已读、订阅和来源/语言/分类筛选均未通过等价性验收，不能打开整个 Feed 的投影读取开关。
5. 不在生产自动运行快照或 journal 清理；只有独立副本验证和保留策略审计完成后才能启用。
