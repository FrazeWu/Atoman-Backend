# Feed COPY: 交叉验证、可取消性、灰度和回滚门禁（2026-11-04）

## 当前状态

- 后端隔离分支 `test/feed-copy-preflight-hardening-20261104` 基于 `612ab6f`。所有实验仍为 **NO-GO 生产**；生产 `main`、HTTP API、数据库、Worker 和 DNS 不变。
- `COPY` 只允许在 `FEED_SCALE_ISOLATED=yes` 且 `FEED_SNAPSHOT_COPY_EXPERIMENT=yes`、连接数据库名称为专用 `_test`、schema 为 `test_<32位hex UUID>` 时执行。**当前没有正式生产 COPY 开关**，这套测试用开关不得被用于生产；它也不意味着生产迁移、Worker 或读端灰度已经具备。
- 之前的独立分支 `ops/feed-rollout-preflight-20261103` 已实现只读预检脚本 `scripts/feed-rollout-preflight.sh`，但没有合并到本分支或在生产运行；其结论仅供制定未来发布步骤参考。测试期的 schema 自动迁移及 revision 触发器不属于生产已生效内容。
- 仅对合成数据和部分 Feed 契约做了 GORM/COPY 对照；所有“速度提升”均需要区分 SQL 写入耗时和含读取、去重、组装、事务的端到端耗时。

## 可重复的 ABBA 反向顺序验证

- 新脚本 `scripts/test-feed-copy-full-abba-isolated.sh 100000` 固定执行 **COPY → GORM → GORM → COPY**。拒绝所有外部数据库 DSN，内部每次委托原有受 CPU/内存约束的临时 PG16 运行器，四组顺序执行，每组生成同分布的 100k synthetic `prodshape` 数据并在结束后清理容器。
- 每次记录首次/二次完整构建、数据库事务写入、去重阶段、代表项计数、深分页、源写入并发、旧代回收；运行结束对组数做跨模式一致性检查，再汇总每个模式的两轮中位数。保存逐轮原始日志，避免只列最佳结果。
- ABBA 不能完全消除共享 VPS 上的并发负载和 PostgreSQL 缓存差异；运行结果仍不可冒充生产 SLA 或代表真实生产文本语料。

## 100k ABBA 完成数据（COPY → GORM → GORM → COPY）

4 次独立 PG16 容器顺序完成，全部退出码 0。每次都跑首次构建和带源数据更新后的二次构建（总计 8 次），91,667/91,924 个去重组、深分页、失效保护、同源并发及旧 generation GC 的检查全部通过。所有数据为 961 源的合成 `prodshape`，日志在远端临时目录 `/tmp/atoman-feed-copy-abba-XyJbsFCF` 中。**测试在共享 VPS 上运行，不能代表生产服务 SLA。**

|---|---:|---:|---:|---:|
| 1 COPY | 16.254 s | 15.821 s | 4.602 s | 2.727 s |
| 2 GORM | 17.413 s | 15.411 s | 6.325 s | 6.469 s |
| 3 GORM | 18.127 s | 14.090 s | 5.940 s | 6.866 s |

## 超时与提交前读者验证

`TestSnapshotCopyContextCancellationRollback` 在两次 COPY 之间以及两段 COPY 之后主动取消 context，并检查旧 head 仍可用且没有遗留 generation/rows/members；同时验证在获取连接之前取消。`TestSnapshotCopyDeadlineExceededKeepsOldGeneration` 使用真实 `context.WithTimeout`，在代表项写入之后等待 deadline，要求全部回滚且同一连接池可以随后成功重建。`TestSnapshotCopyConcurrentReaderBeforeCommit` 在事务未提交的状态下并发查询，确保旧代可见而新代不可见，释放后再验证指针原子切换。以上不替代接近 Worker 120s 预算的大体量超时和故障注入；生产灰度仍需单独验收。

## 未来生产灰度路线（**仅提案，所有阶段须独立批准**）

1. **数据与恢复底座**：先执行独立只读预检，核对数据库容量、已有索引/触发器、RSS 源和负载；备份生产 PG 并完成一次从副本恢复到独立环境的演练。证明可随时回退旧查询路径，并保存变更前配置与版本。此步不安装任何新表或触发器。
2. **隔离副本验收**：在经过授权的脱敏或合成真实形态副本上验证订阅、热门、搜索、混合博客、已读/隐藏等请求不会误入 RSS-only/recent 快照。建立原有 GORM/旧实时路径与 COPY 快照的逐字段、逐页一致性报告及异常集合。
3. **发布架构实现**：未来需要独立、默认关闭、受审计的正式 COPY Worker 开关；不能拿掉本分支的 `_test` 限制来充当上线开关。先完成正式 SQL 迁移的 up/down 方案、触发器副本回归、Worker 超时和审计指标，明确 API 路由和 Worker 的独立控制点。
4. **只写不读阶段**：在批准的变更窗先部署 schema、独立 Worker，以 shadow 方式生成新代但所有用户仍走原 API；每批完成后比对源 revision/checkpoint、代表项、成员、延迟、错误和资源消耗。影子写入和 source 变更日志累积不得在无上限下运行。
5. **读端逐层灰度**：在明确的 feature flag 下仅放开 *RSS-only / recent / 无筛选* 的小比例请求（建议按 1% → 5% → 25% → 100% 的阶段性门禁，非已执行配置）。全部用户继续具备同一旧读路径的同步回退。其它模式一律不接入，直到独立验收。
6. **观察与清理**：至少跨过一个 GC 保留窗口，观察长期运行、频繁写入、较慢读者、WAL/存储增长、autovacuum、RSS 峰值、数据库连接池/锁等待及备份恢复；只有长期数据证明安全才考虑删旧代或正式替换旧算法。

### 建议的灰度暂停/回滚阈值（待与线上真实基线核定）

- **硬门禁**：任何错误代次、部分 generation 可见、数据字段不一致、不能回退旧路径，立即关闭快照读开关。先阻断不安全读，不等重建恢复。
- **任务预算**：目前试验 Worker 单次默认 120 秒；建议受控副本上 p99 全量构建不超过 90 秒（至少留 30 秒余量）再启用 shadow Worker。已有 360k 合成 GORM 84/74 秒、COPY 59/55 秒，不足以得出 p99。
- **读延迟与失败率**：基于发布前基线比较对应 endpoint 的 p95/p99 和实际错误率，发生持续劣化时自动回退到旧查询；不要混用数据库内原始查询毫秒数与 HTTP 耗时。
- **资源与持续性**：明确 Go cgroup 内存、数据库 CPU/锁等待、连接数、WAL 产生量、存储余量、滞后时间、旧代 GC 时长和备份完成状态的告警阈值，任何触及容量/事务安全上限立即停写新代并检查。

### 回滚顺序（不执行，供审核）

先在应用层关闭快照读功能并核实所有受影响请求回退到原有查询；若写入异常，再停止独立 Worker。保留现有 projection/generation/revision/journal 表以便调查、恢复读者并观察旧代 GC，**不直接 DROP/TRUNCATE 或删除检查点**。仅在有已验证备份、恢复演练及独立审批后才能执行 DB 下线或逆向迁移。回滚同时复核 Feed RSS 聚合、订阅、热门、搜索及最近内容是否与旧版本一致。
